# Claude Voice Mod Implementation Plan

This plan connects the existing VoiceMesh Composer experience to the Code tab of Claude Desktop. Composer keeps voice capture, playback, conversation, captions, and turn coordination. A media host consumes the built `@voicemesh/composer` package; a Claude Code Mod supplies session controls and the coding-session bridge. Do not modify or import Composer source files. The first release targets local Claude Desktop Code sessions.

## First usable slice

1. Install the local Mod into Claude Desktop and open a local Code session. Show a voice control and status in `AbovePrompt`; open a pane for captions and secondary controls. Validate the plugin and test a button press in Desktop.
2. Run a local VoiceMesh host that starts Composer's browser audio runtime in a background Chrome process. The host owns provider credentials and exposes an authenticated loopback bridge. Prove capture and playback without Claude task dispatch.
   Use a dedicated settings window with copied DeepSeek connection and voice-picker components. The harness adapter saves provider secrets locally and exposes only configured status to the UI.
3. Bind one Claude session to one VoiceMesh conversation. Send start, stop, mute, status, and transcript state across the bridge. Reconnect safely after Mod reload, `/clear`, `/resume`, and `/branch`.
4. Dispatch one VoiceMesh coding request to Claude with review through `$.prompt.fill()` or explicit submission through `$.prompt.submit({ text, asUser: true })`. Record an accepted result only when submission is confirmed. Never automatically replay a submission with an uncertain outcome.
5. Forward the main turn's final answer or interruption to VoiceMesh for spoken completion. Verify that ordinary voice conversation stays outside Claude's coding prompt and that read-back does not rerun work.

The slice is complete when one spoken coding request can be reviewed or submitted, Claude can finish it, and VoiceMesh can speak the result while the Mod shows coherent status. It must survive one reload without duplicate coding work.

## Bridge contract

The bridge uses bounded JSON messages over a local loopback service. The Mod sends Claude session identity and events with `$.http.fetch` and checks for VoiceMesh commands on a serial timer. Composer's background audio process talks to the same host.

Each coding request carries a VoiceMesh request ID, owning Claude session ID, text, and review-or-submit choice. The bridge reports `pending`, `accepted`, `running`, and terminal outcomes, keeping one request outstanding per session until correlation is proven. Messages carry sequence numbers so reconnects can restore display state without replaying an uncertain Claude submission. A token authenticates the loopback connection; the host binds to loopback only. Provider keys remain in the host.

The Mod controls Claude task cancellation separately from VoiceMesh media stop. `$.turn.abort()` is considered only if the active turn can be proven to belong exclusively to that voice request. Spoken corrections while Claude is working remain in VoiceMesh for review or later submission unless an active-turn steering API is verified.

## Validation and decisions

| Check | Evidence needed | Decision it settles |
| --- | --- | --- |
| Mod runtime | Generated declarations, `claude plugin validate`, Desktop plugin installation, button press in a local Code session | Whether the Mod loads and its UI works in Desktop |
| Host connection | Start, stop, mute, status round trip; browser microphone and playback | Whether Composer can run outside Claude while the Mod controls it |
| Task ownership | One voice request, user prompt, main turn result, unrelated manual turn | Whether a result can be attributed safely to the voice request |
| Failure recovery | Host disconnect, Mod reload, ambiguous submission | Whether reconnection avoids duplicate coding work |
| Steering and stop | An active voice-owned turn and an unrelated turn | Whether any DeepSeek-style mid-turn behavior is safe to expose |

The strongest argument against this arrangement is its extra background Chrome process and unverified real-device behavior. The user should not need to open or keep a media tab visible.

Composer's packed 0.2.0 package owns the speech engines and voice-loop behavior. DeepSeek's harness supplies credentials, session binding, settings, and a coding-task adapter around it. Follow that boundary here: Claude-specific code sends coding text into the active session and returns the result to Composer. The separate pipeline and wake options are still unimplemented in this Claude integration; do not add UI choices until they invoke working packaged Composer behavior.

The strongest limit on exact parity is Claude's Mod boundary: it does not expose DeepSeek's chat-row component or its session controller's active-turn queue, steer, and scoped cancellation contract. These need a supported Claude API before they can be claimed as equivalent. The strongest case for this approach is that Composer already supplies the voice engines and Claude's Mod exposes the coding session, so ordinary conversation and completed coding round trips are demonstrably possible without changing Composer.
